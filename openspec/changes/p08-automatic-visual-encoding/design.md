# 餐厅分类与自动可视化设计定稿

设计已定稿，供另一位 Agent 开发；本目录的任务未执行。用户已确认目的及四类图标，允许在已确认边界内完成技术取舍，不再需要逐个颜色或图标审批。

## 1. 目的与已确认范围

让用户容易识别餐厅的大类，并用细分类别进一步筛选；让接入 Agent 按统一含义标注新地区数据，普通接入无需挑色、画图标或修改业务组件。

| 表达 | 承担的信息 | 决定 |
|---|---|---|
| 图标 | 少量消费形式 | 餐食、小食、甜品、饮品四类；未标注有通用表现 |
| 颜色 | 用于浏览的细分类别 | 复用 cuisine_group；稳定哈希自动配色，接受碰撞 |
| 文字 | 精确含义与来源描述 | 名称、类型、类别与完整 cuisine；不要求仅凭颜色识别 |
| 外圈/文字徽标 | 选中、新晋等状态 | 与类别颜色和形式图标独立，不挤占两种分类表达 |
| 聚合数字 | 当前筛选下的餐厅数量 | 不以其中一家的图标或颜色代表混合集合 |

颜色维度采用用户最后确认的简化范围：既可以是法式、川式等风格，也可以是寿司、拉面等产品类别。本包不要求建立严格正交的风格/产品双重分类，不增加 style[]、product[]、分类树或每种菜品的图标。界面将原“菜系筛选”表述为“菜系与品类”，避免把所有值宣称为纯风格。

不包含：餐厅事实补齐、全量菜系重分类、地图与列表重做、自动推荐、图库服务、碰撞消解、热力图算法改动或真实发布。热力图继续是独立图层；本包的颜色/图标语义仅适用于餐厅标记及对应控件，不能把热力色阶解释成菜系。

## 2. Backward Compatibility Policy

沿用总计划的 [BC-01](../../../docs/plan/plan-260913-0040-frontend-professionalization.md#6-backward-compatibility-policy) 和 [P03 的既有处理](../p03-versioned-guide-coverage/design.md#backward-compatibility-policy--bc-01)。生产使用范围和旧公开接口退役等级没有进一步确认；部署文件存在不作为证据。本包没有接口退役，设计与本地开发可以完整推进。

| 项目 | 本包确定的边界 |
|---|---|
| 页面 | 保留合法 year/city/guide 链接和版本选择、搜索、详情入口；接受用户已经授权的视觉与类型筛选变化 |
| 记录 | 增量增加可选 serving_form；不删除或改变 cuisine、cuisine_group、venue_type 等现有字段含义 |
| 文件/发布 | 保留 catalog、年度文件、固定年度 legacyPath 的既有生命周期；不增加新的别名或双写机制 |
| 旧版本客户端 | 发布使用既有 P07 内容摘要与整包升级/回滚，验证旧客户端不混读新旧资源；不靠清缓存部署 |
| 兼容等级 | 不推定 L0 或永久 L3；本包不新增版本路由、旧到新类型适配层或 feature flag |

venue_type 暂留是保留现有来源字段，不是新 serving_form 的影子字段。新 UI 不同时提供两套形式筛选。未来删除旧字段或旧 URL 单独归 BC-01 决策，本包无需依赖该决定。

## 3. 当前证据与问题位置

设计基线 HEAD：`7245920c454250ff35dfa6cba0853bb6f56a1143`。catalog 登记 7 个地区、13 份年度名单、671 条记录。只读盘点与正式校验支持以下判断，不代表重新核验了逐店事实。

- 东京 taxonomy 有 20 个分组，其中 16 个没有手写颜色；实际可定位星级 157 家中 56 家、Bib 111 家中 76 家因此使用 OTHER 灰色。269 条东京记录均精确映射，数据校验仍通过。
- 当前 `getGroupStyle` 使用手写 COLOR_PALETTE，找不到 key 就返回 OTHER；单元测试明确接受这一行为。
- 旧 venue_type 共 388 个 restaurant、12 个 street_food、2 个 dessert，东京 269 条缺失。该字段并非本次确认的消费目的分类；例如面馆也可能被标为 street_food。
- cuisine_group 已存在风格/品类混用和同义不同 key，例如 SICHUAN / SICHUANESE。前者在本次简化范围内允许，后者影响颜色一致性但归数据规范化，不由渲染器猜测合并。

P08 替代 P04 design 中“新组使用 OTHER 颜色”以及旧 venue 类型控件的具体实现行为；P02 的 raw 精确映射、P03 的版本与来源、P04 的数据集一致性、P05 的坐标资格和 P06/P07 的质量要求继续生效。既有 Packet 作为历史交付不回写成未曾发生的行为。

## 4. 数据与标注合同

### 4.1 四类消费形式

新增 `serving_form?: "meal" | "snack" | "dessert" | "drink" | null`，权威字段规则放进既有 `src/data/contract.ts`。只有一个主值；代码类型由同一 schema 推导。

| 值 | 中文名称 | 定义与边界 | Tabler Outline 3.46.0 |
|---|---|---|---|
| meal | 餐食 | 主营满足吃一顿饭。综合餐厅、面馆、寿司、火锅、汉堡正餐店均可能属于此类，不表示高档或正式服务。 | tools-kitchen-2 |
| snack | 小食 | 主营少量、随手吃或解馋的小食。不能仅根据菜名、价格、摊位形态或旧 street_food 判定。 | dumpling |
| dessert | 甜品 | 主营甜食，如冰激凌、蛋糕、糖水。兼售咖啡不自动变成饮品。 | cake-roll |
| drink | 饮品 | 主营饮用，如咖啡、茶饮、奶茶或酒饮。兼售蛋糕不自动变成甜品。 | cup |

图标只是大类示意；饺子图标不说明店里卖饺子，饺子馆也可以是 meal。分类依据是可追溯的主营供给和主要消费目的，不以单道招牌菜推断整家店。多种供给没有明确主次时留空，不用任意顺序选主值，也不新增 hybrid/mixed/other 枚举。

| 输入情况 | 数据检查 | 展示/筛选 |
|---|---|---|
| 四个合法值之一 | 通过 | 对应类型名称与固定图标 |
| 缺省或 null | 通过，汇总未标注数 | 问号图标＋“类型未标注”；颜色仍正常生成 |
| 空串、其他字符串、数组或错误类型 | 错误，定位到文件/id/字段 | 整个数据集进入既有可恢复错误态，不默认为餐食 |
| 只有旧 venue_type | 旧字段仍按原合同校验 | 不生成 serving_form，显示未标注 |
| 两字段同时存在 | 分别按各自合同校验 | 新 UI 仅消费 serving_form；不要求不同语义的旧字段与新字段相等 |

不新增 unknown 业务值。UI 的“未标注”仅是缺省/null 的派生状态。正式旧记录全部未提供 serving_form 时，允许全部问号；框架验收使用合成夹具覆盖四种已知形式，数据补标由另一个 Agent 承担。

### 4.2 细分类别与原文

继续使用现有字段和结构：`cuisine` 保留完整原文，`cuisine_group` 是一个非空 canonical key；catalog 引用各城市的 taxonomy/mappings。mappings 仍是完整 raw → 一个 groupKey，不引入另一份颜色分类字段或颜色 JSON。

新地区标注规则：

1. 搜索现有城市 taxonomy/mappings，语义相同优先复用同一个稳定 key；显示名称和顺序可以因城市不同。翻译、改显示名不改 key。
2. 类别可以是风格或品类，只表达来源支持的含义：法国菜→FRENCH、寿司→SUSHI、拉面→RAMEN；不因为“在东京”推断成 JAPANESE。
3. 完整复合 raw 由 Agent 判断并显式登记一次。存在明确主体时选择其代表类别，例如“法国菜，现代料理”可登记到 FRENCH；原文完整保留。无明确主体也没有合适已定义类别时用 OTHER，不按第一个词、翻译、地址或哈希决定语义。
4. 新 key 只在现有值无法诚实表达有依据的分类时增加，不为每个风格×产品组合批量建值；key 命名继续采用现有大写 ASCII 规则。增加 taxonomy 和 mapping 后即可展示，无需改样式代码。
5. 新增或修订映射的依据写入既有 mappings.sources 或任务来源材料。来源证据可以来自不同工具；不要求新增逐记录认证系统。

既有 mappings 的分类判断不在本包重新裁定。SICHUAN / SICHUANESE 等不同 key 暂时可能不同色；保证的是“同 key 同色”，不是未经规范化也“同义同色”。数据 Agent 后续合并 key 时应连同 raw 映射、年度记录和来源修订一起对账；这属于有意分类变化。

同一 raw 必须得到同一 groupKey，不允许 Agent 在正式记录中手写一个与 mappings 不符的主值。本版不支持每店自定义覆盖或多色主值。

## 5. 统一展示层与自动配色

### 5.1 归属

复用现有 cuisineRegistry 的责任，建议重命名为 `src/config/restaurantPresentation.ts` 并迁移消费者；不保留第二份样式表或旧转发模块。名字可以由开发者调整，但全应用只有这一处颜色算法、形式展示定义和图标入口。

- 字段合法性/类型：`src/data/contract.ts`。
- 分类含义/城市标签/顺序：现有 taxonomy/mappings；不是前端按英文 key 猜中文。
- 颜色生成、类型名称、图标引用与未知展示：共享展示模块。
- 名称、原文、类型等两端事实：扩展既有 `src/data/display.ts::restaurantFacts`。
- 筛选后餐厅集合：既有 useFilters；地图、统计、热力图从同一集合派生。

四种形式展示定义用 `Record<ServingForm, ...>` 或等价穷尽检查约束；缺少图标定义必须在类型检查/测试中暴露。不建立通用可视化配置平台。数据记录和 taxonomy 禁止携带 color/icon/SVG 作为绕过统一规则的覆盖项。

供 Node 校验调用的规则和常量不得依赖 React、Leaflet、浏览器全局或 Vite `?raw` 导入。渲染适配可以分文件；同一类型/图形定义仍只有一个权威来源，不让校验工具依赖前端打包器。

### 5.2 首版确定性算法

对合法非 OTHER 的 key 使用 FNV-1a 32 位无符号哈希，取 `hash % 360` 为整数色相。初始饱和度 62%、亮度 28%；图标及填色标签文字为白色。输出为标准 HSL 或其等价 sRGB。不引入色彩依赖库。

```ts
// 算法说明，不是已经落地的项目实现。
let hash = 2166136261;
for (let i = 0; i < key.length; i++) {
  hash = Math.imul(hash ^ key.charCodeAt(i), 16777619) >>> 0;
}
const hue = hash % 360;
// background: hsl(hue 62% 28%); foreground: #fff
```

key 的合法域是既有大写 ASCII 规则，因此字符编码没有跨平台歧义。输入不含城市、年度、榜单、显示标签、排序、当前筛选或相邻分类；不做碰撞检测、随机抽色、持久化分配或集合重排。同 key 跨所有上下文结果相同，新增/删除其他类别不改变已有结果。

设计时对 360 个整数色相转 sRGB 的只读计算得到最小白色对比度约 4.93:1；这是参数依据，开发时仍须对实际转换实现和浏览器结果验证。它不意味着任意两种类别色彼此可区分。

OTHER 使用 `#666666`，白色前景；不是因为“样式没登记”使用灰色。未映射 raw 和显式 OTHER 继续由 P02 诊断区分。格式非法或未登记的 groupKey 在合同层报错，不能通过“哈希也能算颜色”绕过 taxonomy 检查。展示函数可以防御非法空值，但该防御不构成数据校验通过。

旧手写颜色表整体退出，包括已知城市；不维护旧色覆盖表。颜色变化是本次设计允许的视觉更新。今后修改哈希/色彩参数应作为明确的视觉修订重测，不在接入新数据时自动发生；不为颜色增加版本路由。

### 5.3 图标素材

采用已确认的 Tabler Outline 3.46.0 四款 SVG，另用静态问号表达未标注；[preview.html](preview.html) 保留图形参考及 MIT 许可。生产建议将四份 SVG 作为本地资产随 Vite 打包，并附来源和原许可；无需引入整套运行时图标库或远程 CDN。

React 与 Leaflet 共用同一份受信图标定义；Leaflet 只拼入本地静态 SVG，不将数据字段当作 HTML、路径或图标 URL。图标解析必须支持离线。具体使用 SVG 资产、静态路径描述或小型组件由开发者决定，不复制两份图形。

## 6. 地图与各消费端

### 6.1 标记和交互

- 首版可见标记直径 32px，图标 20px，线宽 1.8（24×24 viewBox）；位置锚点保持在同一真实坐标中心。白色边沿配深色外缘，使标记在不同底图上保持边界。
- 触摸目标以约 44px 为目标。密集点用现有聚合和 spiderfy 展开提供可选目标，不在重叠点上简单堆放多个透明命中区域。可以调整原 zoom=17 禁止聚合的策略以保证高缩放重叠点仍可展开，不修改餐厅坐标。
- 选中/键盘焦点用外圈与适当层级提示，不替换图标和类别色；NEW 仍按 edition_year/is_new 表达文字，不新增分类含义。
- 混合聚合点维持中性数字标记，数字只统计筛选后且有可用位置的餐厅；展开后再显示各自颜色与图标。不增加饼图聚合或主导类别猜测。
- 无可靠位置仍能搜索、查看详情；不为图标新增坐标或改变 P05 投影规则。

32px 是首版选择；若移动端可读性、碰撞或点击验证失败，可局部调整尺寸/聚合参数并记录理由，不改变四类语义、不扩张地图业务范围。

### 6.2 筛选、图例和详情

| 消费端 | 统一行为 |
|---|---|
| 消费形式筛选 | 用图标＋中文标签替换旧 venue 控件，数据来自 serving_form；默认全部。只显示当前整份数据中存在的已标注类别，顺序按定义表，不随当前类别筛选重排。 |
| 未标注 | 混合数据存在未标注时提供“未标注 N”入口；这是 UI 过滤状态，不存入 serving_form。若整份数据都未标注，保留全部浏览并显示“类型未标注：N 家”，不铺四个无结果按钮。 |
| 菜系与品类筛选 | 当前城市 taxonomy 提供标签与顺序；共享算法提供色样。不生成颜色专属的另一份分类列表。 |
| 图例 | 简短说明“颜色：菜系与品类；图标：消费形式”，复用现有图例/类型控件展示符号含义，不重复铺两份类型长列表。 |
| 两端详情 | 共享事实含类别名、类型名或“类型未标注”、完整 cuisine；显示相同图标/颜色。它们独立于名称、价格、年度和来源。 |
| 搜索与计数 | 搜索命中隐藏记录时启用对应类别并恢复必要形式筛选；未标注也能被显示。显示计数与地图/热力图使用同一筛选结果，切换版本撤下旧选择与详情。 |

类型过滤是已有类别过滤的 AND 条件。形式控件中的 N 以整份活动数据集计数并明确口径；不能悄悄用“已定位”代替全部收录。`unclassified` 可作为纯 UI sentinel，但不是新的数据枚举。

颜色与图标表达不同属性，所以不同图标不能代替菜系文字。所有控件都有可见名称；点位的 accessible name 包含店名、类别和消费形式。支持键盘及触摸查看同样的详情，不依赖 hover。文字前景验证 4.5:1，必要图形/控件边界按 3:1 验证；固定对比底板/边沿承担可测边界，不承诺所有瓦片像素颜色。

## 7. 自动化链路与诊断

```text
来源事实与标注判断
  ├─ cuisine 原文 → 已审阅的完整 raw 映射 → cuisine_group
  └─ 主营/消费目的依据 → serving_form 或缺省/null
                   ↓
现有合同 + catalog 数据校验 + 展示完整性检查
                   ↓
类别 key → 纯函数颜色；形式值 → 四类图标/问号
                   ↓
筛选后的同一记录集合 → 地图 / 图例 / 两端详情 / 统计
```

| 自动承担 | 不由程序推断 |
|---|---|
| boarding 精确映射、保留无关字段；输入输出隔离和原子写入 | 菜系翻译、门店主营、从某一道菜判断消费形式 |
| 新 key 确定性配色、形式穷尽解析、文本安全渲染 | 消解颜色碰撞、根据名字/城市改分类或选择风格主次 |
| enum/引用/映射一致性、样式可生成性、数量与未知汇总 | 补齐 missing、把 OTHER 比例降到某阈值、宣称年度名单更完整 |

复用 `npm run validate:data` 与现有 check/release 管线，不增设平行 CLI：

- 所有被引用 taxonomy 分组（包括尚无餐厅使用的组）均检查可生成有效颜色；非 OTHER 不得落入灰色兜底。展示模块保持无 DOM/浏览器依赖，Node 校验可直接调用。
- serving_form 非法值报 error，包含现有 file/record_id/field 诊断；静态图标缺失、SVG 无效或颜色实现失效由 check/test/构建拦截。
- 在现有 JSON/文本统计中增加四类及未标注数量。缺失只汇总，不逐店制造 warning、不设置覆盖率门槛；保留原 missing_cuisine/unmapped/explicit_other 与坐标诊断。
- `board.py` 仍只改变 cuisine_group，serving_form 和 venue_type 均原样透传。不能在 boarding 中夹带分类迁移。
- 同义 key 检索与新增标签论证属于 runbook 的人工/Agent 判断；自动测试不能声称已经发现所有语义冲突。

标注方法见[来源 runbook 的 P08 节](../../../docs/runbook/runbook-260507-1013-valid-data-source-guide.md#p08-labeling)。现有[接入指南](../../../readme/data-onboarding-guide.md)继续拥有执行命令；P08 开发完成后在原入口启用新字段说明，不复制新接入流程。

## 8. 实施与数据任务衔接

1. 开发先扩展可选字段、共享展示函数和快速测试。正式餐厅、taxonomy、mappings 的字节不因本包重写。
2. 接通地图、筛选、图例、两端详情和组合过滤；用隔离 fixture 包含四类、未标注、相同类别不同形式及有/无坐标。
3. 接入既有校验/发布入口，验证真实东京新类别不再因漏配灰色；读取全部登记数据做展示覆盖检查，不借测试数据改真实名单。
4. 完成任务证据后，将现有 runbook/接入指南的“待实现”提示改为已支持，并写明 serving_form 的实际字段合同；更新相关旧测试，不能继续断言合法新组应回退灰色。
5. 数据 Agent 在支持该字段的版本上独立补标或规范化 key，保留来源、输入/输出和修改字段对账。修改同一年度时遵循既有 revision、aliases/readme 和发布流程。

开发可以在正式 serving_form 全缺失的情况下验收框架；这不等于真实数据已经分类完成。不要为了四类都有示例而推断写入生产数据，也不要把旧 venue_type 批量改名。选择新字段的必要性在于两种含义不同；没有第二套新领域实体或自动适配服务。

## 9. 验收、停止与重新打开条件

[spec](specs/restaurant-visual-encoding/spec.md) 是 P08-R1–R7 的唯一逐项验收正文；[tasks](tasks.md) 记录实现证据和独立结论。框架完成至少需要：

- 合法新城/新 key 无业务代码修改即可自动上色；新增其他 key、排序、筛选和切榜不改原色。
- 四种形式及未知，与任意类别独立组合；所有消费者一致，非法数据被拦截。
- 当前 13 份真实名单仍可加载，已有事实/位置/身份未改；东京缺配色问题消除，形式缺失如实呈现。
- 桌面/移动、键盘/触摸、密集点展开、离线图标和新旧构建切换有适用证据。
- 接入 runbook 可被数据 Agent 直接执行；缺失值、OTHER 和未核验名单不伪装成已验证数据。

允许且不阻断：不同 key 撞色、相近颜色、旧同义 key 未统一、形式标签覆盖率为零。失败并需修正：合法 key 因代码没登记变灰、颜色随筛选变化、用旧类型猜新形式、控件和详情含义不一致、点位无法操作或离线图标丢失。

若今后需要新增第五类形式、一个门店多个主图标、颜色全球同义归并或重构细分类别，应重新说明真实用户任务与数据依据；不通过临时组合值、私有图标表或自动猜测扩张本设计。源码组织、SVG 复用方式、采集工具和测试夹具写法可以改进，只要守住语义、归属和观察到的行为。

## 10. 参考依据

- [Tabler Icons](https://tabler.io/icons)：实际审阅的四款官方 SVG，固定包版本 3.46.0。图标库提供素材，不提供通用餐饮分类标准。
- [W3C Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)：含义有文字等补充；本设计不把类型图标误当作类别颜色的等价替代。
- [W3C Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) 与 [Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)：必要图形可见、目标可操作；44px 为本项目触摸设计目标，非声称所有控件的 WCAG 最小值都是 44px。
- [ColorBrewer 定性色彩原则](https://colorbrewer2.org/learnmore/schemes_full.html)：菜系/品类无大小顺序；本包借鉴分类色原则，不声称所选哈希/HSL 是 ColorBrewer 官方方案。
- [Leaflet.markercluster](https://leaflet.github.io/Leaflet.markercluster/)：复用聚合、缩放和 spiderfy；无需迁移地图库。
