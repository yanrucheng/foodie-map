# 餐厅名单与字段来源核验

执行入口、文件格式、catalog 字段、命令和回滚只在[数据接入指南](../../readme/data-onboarding-guide.md)维护。本 runbook 负责判断证据支持什么；字段合法性归 [P02](../../src/data/contract.ts)，版本与覆盖归 [P03](../../openspec/changes/p03-versioned-guide-coverage/design.md)。采集可用浏览器、HTTP、书籍或人工读取，不绑定特定工具或 Agent。

## 先确认年度与真实地域

1. 找该年度官方发布公告或对应书籍/电子名录，保存原始链接、发布年/版次、地域说明、实际采集时间及原文摘要/材料哈希。edition_year 不等于抓取年份；当前详情页只能支持其明确写出的年份及字段。
2. 枚举官方年度名单身份集合，分页须去重并排除推荐栏，保存稳定 ID/listing URL/分店地址及每页依据。官方总数仅用于辅助检查，A/B/C 与 A/B/D 数量相同仍不完整。
3. scope.description 写实际范围与未知边界；scope.members 的每个成员分别核验。组合名称、现有坐标包围盒或观测到的地址不证明完整地域边界。
4. 把年度、范围、名单来源登记到 provenance.sources；完整身份对账指向 coverage.reconciliationPath。记录采集/核验的真实时间，历史未知填 null；迁移时间写任务记录，不冒充采集时间。

官方零收录必须有适用于该年、该榜单、该范围的明确证据和空官方身份集合。没有文件是 not-collected；空 JSON 是未核验空名单，除非另有官方零证据。已发布缺文件是错误。未恢复完整官方集可保留 partial/unverified 并提供受限浏览。

东京现有材料支持 2026 公告总数、当前在线身份、KIBUN 年度入选及 partial；不支持完整年度身份集或排他性 23 区范围。catalog 已直接引用原材料，不能因为现行分页对齐把年度升级为 verified。

## 当前名单来源边界

旧 11 份名单保留文件自报的 2026 年版；历史采集时间、官方年度范围和完整身份集合仍未知，保持 unverified。广州·深圳分别说明成员范围，当前详情 URL 不能证明历史名单完整；不把迁移日期当作采集日期。

东京的年度公告、在线身份和字段来源见 catalog 直接引用的[采集说明](../../eval/sessions/260914-1037-tokyo-michelin/report.md)及 edition/list/record 材料。2025-09-25 官方公告支持 2026 年版和 160 星级、114 Bib 总数；现存星级 157 个在线身份加年度 KIBUN 共 158，Bib 111，缺少 2/3 个年度身份，保持 partial、verifiedAt=null。观察到 19 个特别区不证明仅限 23 区。

年度文件是餐厅事实的维护源，catalog 负责发现与来源声明。JPY、KIBUN 缺坐标及其他已登记字段继续保留；当前营业状态不决定历史入选。旧无年路径是固定年度的派生副本，同版修订仍需填写 revision.id/reason/evidence。历史开发过程的迁移日志与候选压缩包已清理，接入和校验使用当前数据及本 runbook。

## 按字段找权威来源

| 事实 | 首选依据 | 限制 |
|---|---|---|
| 年度入选、星级、Bib、新晋 | 对应年度 Michelin 公告/名单；该版明确标识的详情/结构化数据 | 当前 NEW 标记、当前详情存在不证明历史名单；promoted 不自动等于新晋。 |
| 原名、原始 cuisine、地址、价格等级 | Michelin 对应 listing | 不按翻译猜身份，不把等级换算金额。 |
| 金额、电话、官网、当前营业变化 | 餐厅官网/菜单或明确官方来源 | 保留原价条件与币种；当前停业/搬迁独立于历史入选。 |
| 坐标 | 同一餐厅 Michelin JSON-LD；否则合适地图来源并核对名称与地址 | 统一输入 WGS84 约定；高德等提供的其他坐标系须按 P05 规则确认转换，不能原样冒充。 |
| cuisine_group | 本地 taxonomy/mappings 确定性派生 | 完整 raw 精确匹配；未知 OTHER，不造来源菜系。 |

中文/英文名、地址、价格、官网均允许按合同缺失，不为凑齐模板制造值。保留 listing URL 但记录其失效事实；KIBUN 当前下架不能推断停业，也不能删除其历史入选。

## P09 主打体验、菜系与价格标注（本地框架已实现）

本节是用户已确认的后续标注标准：八类主打体验图标、原有菜系自动颜色、独立价格角标。字段与工程合同见 [P09 design](../../openspec/changes/p09-dining-experience-markers/design.md)，开发/验收状态见 [P09 tasks](../../openspec/changes/p09-dining-experience-markers/tasks.md)。**dining_category 已进入正式可执行合同，八类图标、价格角标、筛选及分榜单诊断已接通。** 按本节核实后可在授权的数据任务中填写年度数据；工具与命令见[接入指南](../../readme/data-onboarding-guide.md#权威入口与输入)。开发验证、正式数据补标和独立验收分别见 tasks，框架支持不代表正式标签已经核实。本节旧 p08-labeling 锚点保留为阅读入口，不继续要求新任务按四类主图标补标。

### 一店一个主打体验

目标字段是可选 `dining_category`。判断单位是同一门店的主要用餐体验，回答“人们主要来这里吃什么”。不计算碳水/肉类占比，也不要求店里只卖一种食品。

| 值 / 图标名称 | 选择依据 | 边界 |
|---|---|---|
| staple / 面饭面点 | 面、饭、饼、饺等成品是主要卖点，如拉面、意面、饭团、披萨、饺子 | 牛肉面仍可归面点；寿司、鳗鱼料理按约定归鱼鲜，不能看见饭就归此类 |
| meat / 肉食主打 | 肉类是主要卖点，如烧鸟、猪排、烤肉、涮羊肉、以烤鸭为核心的餐厅 | 可以同时卖凉菜和面点；普通综合餐厅有一道招牌肉菜不足以证明肉食主打 |
| seafood / 鱼鲜主打 | 鱼、贝、蟹等为主角，含寿司、鳗鱼、蟹料理和明确鱼鲜主打的套餐 | 沿海地方菜、菜名中出现鱼，或部分天妇罗材料是海鲜，均不足以直接推定 |
| dessert_drink / 甜饮 | 主要体验是甜品或饮品，包括水果甜品套餐、咖啡、茶饮和酒饮 | 二者合并共用图标；饮品不要求甜味，正餐附带甜品/酒水不算 |
| french / 法式 | 没有更明确食品主打的综合法国料理，含现代法餐和法式小馆 | 有明确甜品、肉食等主轴时食品主打优先 |
| chinese / 中餐 | 没有更明确食品主打的综合中式料理、地方菜 | 地方风格继续由 cuisine_group 表达；不能按所在城市推断属于中餐 |
| japanese_course / 日式会席 | 会席、怀石及以多道和食组成一餐的同类套餐；允许割烹等供餐形式 | 用户接受宽口径；必须有套餐/菜序/供餐结构依据，仅“日本料理”、星级或高价格不够 |
| other / 其他料理 | 有依据的未单列料理，例如综合意餐、综合素食、混合食材的天妇罗等 | 表示已作出的分类判断；尚未判断或证据不足不能为提高完成率统一填 other |

判断顺序：

1. 优先判断有充分依据的面饭面点、肉食、鱼鲜或甜饮主打。四者没有任意的字面抢占顺序，按主要卖点判断。
2. 没有突出单一食品，或多种食品同样重要时，按整体供餐判断法式、中餐、日式会席等综合类别。
3. 已确认的经营样态不在前七类，使用 other。无法支持任何一个判断时省略字段或填 null。

以下情况必须能够按同一规则解释：

| 来源支持的经营定位 | 主分类 | 原风格/价格如何处理 |
|---|---|---|
| 牛肉面馆；以意面为主轴的意式套餐 | staple | 原菜系和价格保留，肉/意式不覆盖主打成品 |
| 寿司、鳗鱼料理；明确以鱼介为主的中餐 | seafood | 可保留 SUSHI、UNAGI、CHINESE 等原色组 |
| 涮羊肉为核心的火锅；烤鸭为核心、兼售其他菜 | meat | 不要求菜单只有肉；鱼鲜锅不能套用肉食判断 |
| 主要是水果甜品的多道套餐 | dessert_drink | 套餐或高价不使其成为综合正餐 |
| 会席中肉、鱼、蔬菜均重要；有明确多道和食结构 | japanese_course | 菜系文字保留；和牛尽食套餐以肉为主时可归 meat |
| 只有“日本料理”，没有可支持套餐或主打的信息 | 缺省/null | 不因在东京、米其林星级或价格高而补会席 |
| “本帮菜/点心”“粤菜/面食”等复合标签 | 先核实主打，再选 staple 或 chinese 等 | 不按“包含点心/面食”自动覆盖综合类别；原文完整保留 |

预览中 27 家东京日式会席含 23 家依据简介初拟，7 条复合面点标签也使用了快速试分；它们不是已核实的正式标签。接受宽口径标准不等于确认每条试分事实，不能直接从预览导出覆盖年度数据。

### 证据、缺失与历史字段

优先使用同一门店的官方经营介绍、菜单和可保存的 Michelin 说明。原始“拉面”“寿司”等标签在语境充分时可直接支持对应主打，无需为了形式重复抓取菜单；笼统菜系、单个招牌菜和历史训练经历只作线索，是否足够要看完整上下文。

在已有任务材料中保留 city/year/guide/id 或稳定 listing 身份、变更前后值、来源 URL/摘要及适用时间、判断理由。可以复用东京 serving_form 核实材料中的官方摘录；不以旧 meal、snack、dessert、drink 的字面值自动转换。无需新增逐店证明文件、独立认证服务或强制采集工具。

缺省/null 在数据上保持未标注。界面共用其他料理的刀叉图形，但详情和统计区分状态；不能把图形出现当成标注完成。合法值只有表内八项，unknown、mixed、空串、数组、旧类型值及预览内部 sweet/kaiseki 均不能作为新字段值。

原 serving_form 与 venue_type 的已存事实保留，不改名、不批量复制、不为凑字段而双写。新接入任务优先按本节提供 dining_category；旧字段未提供不妨碍新主分类成立。若某次任务专门修订历史字段，按该字段原合同及来源单独对账。

### 再确定用于颜色的细分类别

继续使用完整 `cuisine` 原文、taxonomy 和 mappings 派生的单值 `cuisine_group`。颜色维度允许风格和产品类别，显示为“菜系与品类”；不新增纯风格字段、产品字段或层级分类树。dining_category 是门店的主打体验，两者可独立组合。

1. 查找现有各地区 taxonomy/mappings。相同含义复用稳定 key，展示名称可按城市使用不同语言或文字；不要因来源翻译差异新建同义 key。
2. 用来源支持的精度标注：法国菜可以归 FRENCH，寿司可以归 SUSHI；只有中国料理就保留已定义的 CHINESE，不根据所在城市、店名或菜单中的一个词猜地方菜。
3. 完整复合标签只登记一条确定映射。存在明确主体可选其代表类别；没有主体且无适用既有类别时用 OTHER，保留完整原文和判断说明。禁止运行时拆首词、翻译兜底或在记录里覆盖 mappings 结果。
4. 现有值无法诚实表达有依据的分类时，可增加 taxonomy key、中文/英文名称、sortOrder 和完整 raw mapping。新 key 采用既有大写 ASCII 格式；尽量命名为可跨城市复用的语义，不用城市/年份/颜色名充当类别。
5. 新增或修订 mappings 的依据使用已有 sources 或任务材料保存。旧 key 的合并需要全量检查其引用，不在单个地区悄悄改变同 key 的含义。

框架对任意合法非 OTHER key 自动配色；接入 Agent 不选择色值、不新增图标、不维护每城样式表。新 key 可能撞色是正常情况，不能为换颜色而改 key。用于菜系颜色的 OTHER 与用于主打体验的 other 是不同字段；不能互相覆盖。P09 沿用 P08 颜色能力。

### 独立保存价格

price_range 只填写该 listing 明确提供的价格等级原文，如 ¥¥、$$$；price 与 currency 保留真实价格的原文和条件。没有等级就省略/null，不按星级、地区、菜系、实际金额或希望显示的符号数估填。

前端在解析副本上规范化，并把 1–4 个相同货币符号识别为等级，角标统一输出同数量的 ¥；港澳 $ 的原始字段和币种不变。这是等级显示，不是换汇。缺失或无法识别的非空等级文本不显示角标，后者在诊断/详情中保留；不要为了显示角标清洗或覆写真实原文。

新数据只提供既有价格字段，不存 price_tier、badge_text、P1–P4、问号或横线占位。价格不参与主打分类。

### 生成、检查和交接

按[原接入指南](../../readme/data-onboarding-guide.md)使用已有年度数据、catalog、taxonomy/mappings、boarding、aliases、校验、覆盖生成及对账命令。boarding 仍只改变 cuisine_group，dining_category、历史类型、价格和其他原始事实原样透传；正式字段合法性由共享合同校验。

逐城市×年度×榜单交接：

1. 八类显式值和未标注数量；显式 other 与未标注单列，合计与收录数对齐。
2. 四个价格等级、缺失和无法识别数量；说明缺价点位没有角标。
3. 最大图标组及其占比、最大同图标同价位组及其占比；保留分榜单结果，城市合并只作补充。
4. 未映射 raw、需要补来源的身份/标签及改了哪些字段。字段修订、身份集合、名称、评级、价格和位置按授权范围对账，名单覆盖仍按年度证据判断。

不设最低补标率或最大类别占比，不为均匀而把餐厅塞进人数少的类，也不把所有未知写 other。集中度高时先核实是否有真实的肉食、鱼鲜、面点等主打被笼统菜系遮住；若分类体系确实承接不了，由产品层统一调整枚举，不能各城自己改含义。

P09 框架用隔离夹具验收；正式补标是后续独立数据任务。当前 Tokyo 的旧形式核实可复用证据，新字段仍需另判。开发完成、真实补标完成、独立验收和部署分开报告。既有菜系同义 key 规范化也不混入图标开发或未获授权的数据修改。

## 分店、改名、迁址与年度对账

采用官方稳定 ID 或归一化 listing URL。跨语种只移除 URL locale；地域及分店 slug 保留。同名不能合并。改名/URL 变化的人工例外写 aliases.from/to/evidence/reason，需明确一对一证据；有冲突先保留歧义，不猜匹配。

运行指南中的 data:diff，检查官方输入和所有匹配依据。报告明确区分年度退出、采集漏项和待核实，当前 status/address/website 变化单独列出。同版修订必须有 revision.id/reason/evidence，结合任务/Git 及发布内容摘要追溯。若需要保存搬迁前地址事实，在证据记录旧值与修订理由，不能静默覆盖历史含义。

## 位置与缺口

地图候选需对名称、城市、区街、建筑/分店上下文。来自搜索摘要、模糊同名、区中心、邻店/酒店默认点均不足以确认。多个餐厅同点只触发复核，确实共享建筑可能合法；不因重复自动删店或清空 flag。

缺可信坐标用省略或 null/null；候选可按 P02 标 geocode_success=false。0,0 不合法。geo_source 写实际来源，不伪造成功。名单完整度与可定位数量分别计算；合同可定位不代表 P05 的真实道路/建筑精度验收。

## 交接与异常恢复

维护当前数据需要的输入名单、年度范围依据、采集/核验时间、来源材料和人工例外；本轮变更运行身份对账与校验。报告证据缺口与它影响的结论，不以“校验通过”代替官方完整性。发布前运行指南规定的校验/覆盖/浏览器/性能门禁；任何门禁失败先保留日志并定位原因，不用空检查器或弱化断言绕过。

回滚恢复同一已检查候选的 catalog、年度文件、分类和构建；旧公开 JSON 由固定年度派生，不双写。网页合法 year/city/guide 链接保留；BC-01 的退役决定独立待定。新增覆盖直接按[数据接入指南](../../readme/data-onboarding-guide.md)执行，不依赖历史开发证据。日志、截图和候选快照写入被忽略的 test-results/ 或临时目录，完成本轮排障后即可清理。
