# 餐厅中文正式名称纠正

北京 8 家小样已完成开发并通过独立验收。2026-09-25，orchestrator 转交用户对完整正式门店名口径和全量范围的直接确认：「确认，推进国内 402 条（含港澳，排除东京）」。本计划现按该授权实施全量名称核实与修正；小样历史要求保留在下文，全量完成仍须独立验收。授权不包含发布或部署。

## 目的与权威归属

目的：让用户看到和搜到能由同一门店正式来源支持的名称，消除音译猜字、错误汉字和分店混淆。这里的正式名称指餐厅对外使用的门店名称，不是工商主体名称。用户已确认采用小样所示的完整正式门店名口径，包括「京艳 ‧ 翰林书院」。

沿用 [数据接入指南](../../readme/data-onboarding-guide.md) 和 [来源 runbook](../runbook/runbook-260507-1013-valid-data-source-guide.md)：

- 年度餐厅 JSON 是字段唯一维护源；旧无年路径由 `data:aliases` 派生，不手写两份。
- `catalog.json` 负责发现、来源引用和同版 revision；不新增名称注册表、翻译字典、正式字段或审批服务。
- 来源语义由现有 runbook 承载。用户确认后，开发已将可复用的名称证据规则补入其“按字段找权威来源”段；本计划保留本次范围与验收安排，不作为第二份长期规则。
- 本轮逐店依据、差异和验收结论沿用 [eval 会话](../../eval/sessions/260925-0915-chinese-restaurant-names/report.md)。该目录是维护凭证，不参与前端名称选择。
- 展示与搜索仍复用 [display.ts](../../src/data/display.ts)。现有 `displayName` 优先使用 `name_zh`，`searchNames` 同时搜索 `name/name_zh/name_en`。目前没有发现在线模型生成中文名的路径；错误已写进数据，不能仅靠 UI 覆盖。

调查基线：Git `34763f4e1b71c038e8a2bace80c0bcb90b4fba48`，服务 `0.3.0`。catalog 共 671 条年度记录；国内 402 条，东京 269 条。用户指出的记录是 `beijing/2026/michelin-starred#11`，`name_zh=京雁`，`name=京雁 / Mansion Cuisine by Jingyan`，地址箭厂胡同22号。旧 P09 证据只有英文名，不能据此推导中文写法。

## 证据判定的不变量

1. 首选餐厅/所属酒店明确官方门店页面、菜单或官方账号原始材料；同一门店 Michelin 中文 listing 可直接支持正式收录名称。本小样采用后者。来源有冲突时展开核实或保留未决，不以多数搜索结果决定名字。
2. 门店对应至少核对保留地域/分店 slug 的 listing 身份及地址上下文。沿用现有 `listingIdentity` 的语义；只剥离语言、query/fragment、末尾斜线，不删分店 slug。相同品牌不是相同门店，文件内数字 id 不是跨文件全局 id。注意目前实现只去掉双段 locale（如 `/sg/zh_CN/`），仍保留单段 `/en/`，两者返回值直接比较会不等。本轮已有明确原 URL→中文 URL 对，须检查去掉各自已知 locale 后的完整路径以及地址，不能据此误判不同店或另行模糊匹配。如果开发选择修复共享 helper，应补单/双段 locale 与不同分店的必要回归测试；不要求为了本次数据纠错扩建匹配系统。
3. 依据必须是目标页面主标题/明确的门店名称及地址，不是相关推荐、导航、搜索摘要或模型翻译。中文 URL 不代表内容一定中文；重定向和英文回退必须检查。 HTTP 200、202 或抓取成功本身都不能证明名称。
4. 保留来源原文字面值；候选只可做已披露的排版处理。本小样把分店括号统一为中文全角并去掉其前空格，保留正文汉字和「京艳 ‧ 翰林书院」中的原始间隔点。不得凭习惯替换同音字、品牌异体字或省略分店限定。港澳不得批量简繁转换。
5. 当前页面可以证明当前观察到的同一门店名称，不能证明整年始终使用该名称、历史获奖完整性或新的星级。出现真实改名、搬迁或身份冲突时记录变化，不能当作错字静默改写历史。
6. 没有中文名称证据就不造中文名。只有正式外文名时可以保留已证实的外文品牌写法；页面不可读或身份不清时列为未决，不自动覆盖、清空或宣称正确。若全量必须清空未经证实的旧中文名并回退外文展示，该处理须先让用户明确确认。

取证方法开放：HTTP、浏览器、可靠存档、官网原文或人工阅读均可。设计阶段的浏览器抓取只是可用方法，不是新的长期执行合同。

## 开发交付要求

### 可直接查看的候选

沿用本 eval 会话，提供 `outputs/preview.html` 和开发启动的本地 HTTP 地址，供用户直接打开。可用静态页或现有技术生成，无需改应用导航或增永久产品功能。8 行/卡片逐条显示：原显示名、候选名、修改或保持、城市/分店地址、官方来源原始主标题、原始地址、来源链接及读取时间、具体理由和未决事项。原文与排版后的候选分开显示；“京艳”行置顶，页面标题标清“北京 8 家小样，待用户确认”。

原始页面保存在 `outputs/sources/`，预览提供本地证据入口，不能要求用户自行读 JSON 才能判断。名称和来源正文按普通文本转义，避免抓取 HTML 被当成产品代码执行。外部来源点开可能再次遭遇访问限制，须保留可读原文摘录；原始 DOM/截图是补充，不可用空白截图假充依据。

小样候选使用既有数据合同。建议在 `outputs/candidate/public/data/` 放完整 catalog 数据根，只更改选中记录；使用现有 `--root` 校验和 aliases 能力。可用等价隔离方式，但必须保证用户确认前正式 `public/data/` 不受小样污染。开发选用现有 preview/test server 时避开其他 surface 的端口，不中断用户现有服务。

另外提供真实应用的小样预览入口或可复现浏览器检查：从该候选输入读取，核实搜索结果、详情及地图弹窗显示新名；京艳可以搜到 #11，两个新荣记分别对应正确门店，英文名仍可搜到。必须证明应用消费了候选，不能只把独立对照表当作应用验收。

### 精确数据差异

仅 starred #7/#11、bib #10/#13 的 `name_zh` 和含同一中文片段的组合 `name` 改动；保留原 `name_en`。其余 4 条保持整个记录原值（TRB 的旧重复组合名属于另一个清理问题，本轮不顺带修改）。不做全局字符串替换，不把旧错字作为新别名继续写进组合名。

本轮不改 id、guide_url、city、edition_year、入选身份集合、评级、新晋、status、地址、坐标、价格、菜系或体验类别。旧证据中的历史错字是当时原值，保留以便追溯。

候选内更新受影响两个榜单的 `provenance.revision.id/reason/evidence`，保留之前 revision 到本轮证据，复用现有 sources 结构。coverage、collectedAt、verifiedAt 保持原语义；来源阅读时间只写本轮证据，名称核验不能升级名单 coverage。旧路径经 `data:aliases -- --root <候选数据根>` 生成。若未来原地应用，更改正式数据后按指南生成覆盖表摘要，不能伪改日期或名单数量。

### 开发回交

提供预览 URL、候选目录/哈希、逐字段前后差异、验证命令与结果、真实应用检查材料、未决项；附小样正式数据未变的对账。复用 [report.md](../../eval/sessions/260925-0915-chinese-restaurant-names/report.md) 追加开发结果，不创建状态系统。提交给 orchestrator 转独立验收；失败项由其转开发修复后复验。

## 独立验收标准

| 检查 | 通过要求 |
|---|---|
| 来源与同店性 | 8/8 逐条人工核对来源主标题和地址；原文、候选及排版转换一致；金融大街/新源南路两店不串；来源原始页面存在且 SHA-256 可复验 |
| 修改边界 | 恰为上述 4 条记录、8 个字段；4 条保持项无改动；全量身份、记录数及非名称事实完全保持；正式 public/data 小样阶段不变 |
| 用户可读 | 无需查看 JSON 即可看清 8 家的旧名、新名和原文依据；链接和本地摘录可打开；标题不宣称用户已批准 |
| 应用效果 | 从候选驱动的实际应用中，搜索/详情/地图弹窗一致；京艳和英文可找到目标店；京雁不残留在该候选的任何名称字段；分店匹配准确 |
| 结构与派生 | Node/npm 遵守项目版本；`validate:data -- --root <候选数据根>` 通过，legacy 副本与年度源字节一致；source/revision 引用有效；不更改 coverage |
| 未决项 | 证据缺失、语言回退、地址冲突、真实改名均明示，不猜名；当前 8 条无未决中文改写，#7 建筑称谓差异已披露 |
| 授权闸门 | 验收者只能报告“小样通过，待用户明确确认”；无用户明确确认，不能运行全量修改或发布 |

同版前后差异用本轮 baseline 和逐字段比较，现有 `data:diff` 要求跨年，不可伪造一个新年度来用它。保留 id/URL/数组顺序并比较所有非白名单字段。纯数据纠错无需为每家新增镜像单测；复用合同检查和实际应用检查。若开发改动共享脚本/展示逻辑，额外运行受影响既有测试；正式全量完成再按接入指南完成 check、test、coverage、release:check 和 release:verify。发布仍属独立动作，门禁成功不授权部署。

## 用户确认后的全量范围与完成条件

用户已明确确认现有 2026 国内 402 条年度记录（下表），包括内地 221 条、港澳 181 条，排除东京 269 条。原确认问题为：「看过小样 http://127.0.0.1:55229/review/preview.html 后，是否确认采用其中的完整正式门店名口径（如『京艳 ‧ 翰林书院』），并按以下范围推进全量？」用户直接答复：「确认，推进国内 402 条（含港澳，排除东京）」。该答复由 orchestrator 在开发会话原文转交；不是设计者验收替代用户确认。现可修正正式年度名称字段并生成派生副本，无需重复确认已授权范围。

全量按同样证据要求逐店核验，不按拼音批量猜字，不把未经阅读的语言 URL 当作来源。每条最终有“有证据修改 / 有证据保持 / 正式外文名保持 / 未决”明确结果。总数必须与授权分母一致；所有修改由验收者复核原文与身份，所有保持项也须有逐店依据。未决不能藏在通过率中；未决名称影响授权目标时，全量不能宣布验收通过，须补证或由用户明确缩小/调整处置范围。

全量通过需要：授权范围逐店处理完成、身份集合与非名称事实对账通过、年度源与派生副本一致、证据与 revision 可追溯、实际应用显示和搜索验证通过、项目必需门禁通过。最终报告区分“全量本地数据完成/独立验收通过/是否发布”。小样验收、用户确认和全量验收是三件不同的事实；用正常会话和本 report 留下真实结论即可。
